# AI Incident Analyst: integration and production boundaries

## Interfaces

The same integrity-checked evidence layer is available through three routes:

- LangChain structured tools inside the LangGraph workflow;
- an MCP 1.26 stdio server (`python -m app.ai.mcp_server`);
- versioned JSON artifacts generated by reproducible demos.

MCP accepts only a scenario and optional run UUID. It cannot execute SQL or
read paths supplied by a client. The server resolves artifacts below the
configured results root and verifies their SHA-256 digests before returning
evidence.

## Delivery and observability

`--publish-kafka` publishes one `taskgraph.ai.incident.completed` event. The
event contains identifiers, scenario, status, selected tool names, aggregate
validation/source counts and latency. It deliberately excludes the user
question, prompts, raw evidence, database credentials and report text.
Publication uses bounded retry and at-least-once semantics; consumers can use
the stable `analysis_id` as an idempotency key.

Prometheus exposes bounded-cardinality metrics for:

- analysis status and duration;
- selected tools;
- validation-error counts;
- attached RAG-source counts;
- Kafka delivery outcomes.

## Acceptance and limits

`python -m demos final-smoke` runs 20 offline grounded-agent evals, starts a
real MCP client/server exchange and verifies metric registration. With
`--publish-kafka`, it also publishes the latest validated analysis event.

The current hash embedding is a deterministic local baseline, not a claim of
semantic retrieval quality. The fixed 20-case evaluation proves regression
behavior only for its checked dataset. Production rollout would additionally
require a production embedding model, authentication/authorization for a
network MCP transport, Kafka topic policies, traces and a larger labeled eval
set.
